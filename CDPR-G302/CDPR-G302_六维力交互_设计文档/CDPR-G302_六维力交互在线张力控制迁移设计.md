# CDPR-G302 六维力交互在线张力控制迁移设计

## 1. 文档目的

本文基于以下两份程序的实际代码进行比对：

- 当前程序：`CDPR-G302`，已经完成六维 F/T、Newmark 虚拟动力学、阶段 D0/D1、在线速度控制、工作空间边界、集中式 SafetyMonitor 和离线记录；
- 参考程序：`allforce_test_0905_1409`，没有六维力交互，但包含【8绳力矩参数】对应的八绳任务空间力矩控制与可选 0525 张力内环。

目标不是把参考程序整页或整套 `MainWindow/ControlWorker/HardwareInterface` 搬入当前程序，而是提取经过验证的算法核心，在当前六维力交互中增加一个低耦合的“在线张力/力矩执行后端”。现有在线速度 D1 必须保留，并继续作为默认和回退方案。

本文只规定迁移边界、接口、实施顺序和验收方法，不表示在线张力控制已经接入当前程序。

## 2. 术语与目标控制链

本文所称“在线张力控制”不是向位置命令叠加绳长补偿，而是参考程序【8绳力矩参数】页对应的控制链：

```text
六维 F/T
  → 去零、滤波、门限和坐标变换
  → Newmark 虚拟动力学
  → 期望位姿 / 速度 / 加速度
  → 六维任务空间跟踪控制
  → 六维广义控制力旋量
  → 八绳冗余张力分配
  → 八路目标张力
  → 可选 0525 实测张力内环
  → 八轴电机转矩命令
```

外力只在 Newmark 中进入一次。任务空间力矩控制器不得再次叠加同一六维 F/T 外力，否则会重复计算外力作用。

### 3.4 已发现的公共依赖差异

两份程序中同名的 `forcepid0525.*`、`MatrixFun.*`、`winchcompensation.*` 和 `forwardkinematicssolver.*` 内容并不完全相同；参考程序还额外使用了 `mocapposeobservation.h`、`eightcabletracesummary.h` 和 `eightcableencodervelocity.h`。

因此迁移时必须逐项合并所需能力，不能用参考版本覆盖当前文件。凡是几何、绞盘、单位和轴映射数据，均以当前 `MachineKinematicsProfile` 及当前六维力准备会话冻结值为准。

## 4. 低耦合总体架构

### 4.1 基本原则

1. 六维力前端只产生“期望平台状态”和停止意图，不直接关心后端是速度还是转矩；
2. 执行后端只接收冻结配置、期望状态和统一反馈，不读取 UI；
3. 算法层不调用雷赛 SDK；
4. 只有 `ControlWorker` 拥有运动命令调度权；
5. 每周期先 `propose`，硬件八轴批量命令成功后再 `commit`，失败则丢弃候选状态并急停；
6. 速度后端与力矩后端互斥，准备时冻结，运行中禁止切换；
7. 全局 SafetyMonitor 继续是张力、实际转矩、状态字、行程和看门狗的最终安全裁决者。

### 4.2 建议模块划分

```text
ForceInteractionRuntimeControl
  ├─ 公共：F/T调理、Newmark、工作空间、时钟、制动、会话记录
  └─ 输出 ForceInteractionReferenceFrame
                 │
                 ▼
ForceInteractionActuatorBackend（窄接口）
  ├─ ForceInteractionVelocityBackend（封装现有逻辑）
  └─ ForceInteractionTensionTorqueBackend（新增）
         ├─ TaskSpaceTorqueController
         ├─ RedundantTorqueAllocator
         ├─ EightCableTensionFeedback（可选）
         ├─ EncoderPoseObserver / FK外环
         └─ TorqueModeLifecycle
                 │
                 ▼
ForceInteractionActuatorDispatcher
  ├─ 八轴速度批量下发
  ├─ 八轴转矩批量下发
  ├─ 停车/急停
  └─ 力矩模式退出到位置保持
```

不建议让 `ForceInteractionTensionTorqueBackend` 继承或直接操纵 `ForceInteractionRuntimeControl`。二者通过值类型数据交换，便于单元测试、离线复算和后续替换。

### 4.3 公共参考帧

建议新增不含硬件句柄的值类型：

```cpp
struct ForceInteractionReferenceFrame {
    quint64 sequence;
    qint64 sourceMonotonicUs;
    double modelTimeS;
    ForceInteractionPlatformState desired; // pose/twist/acceleration
    bool interactionTriggered;
    bool braking;
    bool valid;
};
```

`desired` 必须是本周期已经完成全部 Newmark 补算、边界判定和协同减速处理后的最终参考。后端不得再次推进 Newmark，也不得自己解释 F/T。

### 4.4 公共反馈帧

建议在当前 `ForceInteractionRuntimeFeedback` 基础上扩充，而不是另造一套硬件快照：

```cpp
struct ForceInteractionActuatorFeedback {
    // Trace公共质量信息
    quint64 logicalFrameSequence;
    qint64 monotonicUs;
    qint64 newestFrameAgeUs;
    bool reliable;

    // 八轴
    Axis8 position;
    Axis8 encoderVelocity;
    Axis8 measuredTorqueNm;
    Axis8 tensionN;
    StatusWord8 statusWord;

    // 平台实际状态
    ForceInteractionPlatformState observedPlatform;
    bool observedPlatformValid;
};
```

该结构由 `ControlWorker` 从一次完整 Runtime Trace 快照及一次明确的位姿观测结果构造。后端不得自行读取 Trace、Nokov 或全局变量。

### 4.5 后端命令与两阶段提交

```cpp
enum class ForceInteractionActuatorAction {
    None,
    CommandVelocity,
    StartTorque,
    ChangeTorque,
    HoldTorque,
    ReturnToPositionHold,
    NormalStop,
    EmergencyStop
};

struct ForceInteractionActuatorProposal {
    ForceInteractionActuatorAction action;
    Axis8 velocity;
    Axis8 torqueNm;
    Axis8 targetTensionN;

```

后端的积分量、PID状态、上一目标张力和上一已提交转矩，只能在八轴批量命令全部成功后提交。任一轴失败、部分下发或超时均不得把候选状态当作已经执行。

## 5. 流式 Newmark 参考的接入方法

### 5.1 不沿用预规划轨迹接口

参考程序的 `EightCableTorqueControl` 通过 `prepareReferencePlan()`、`stageReferencePlan()` 和 `startReferencePlan()` 管理完整轨迹，运行时对 `TaskSpaceTrajectoryPlan` 采样。这与六维力交互每 5 ms 才产生下一个 Newmark 状态不匹配。

禁止采用以下临时做法：

- 每 5 ms 构造一个短轨迹段；
- 每周期重新 stage/start；
- 用 UI 线程不断改写控制器目标；
- 把 Newmark 输出伪装成旧程序的预规划整段轨迹。

这些做法会破坏参考时钟、状态连续性、命令归属和停车语义。

### 5.2 新增流式参考端口

力矩后端每个外环时刻读取最新的 `ForceInteractionReferenceFrame`：

- `pose` 直接作为任务空间期望位姿；
- `twist` 作为期望线速度/角速度；
- `acceleration` 作为期望线加速度/角加速度；
- 使用参考帧自己的主机单调时间和序号检查新鲜度；
- 参考没有更新时只能在限定寿命内保持上一已提交参考；
- 参考过期时进入受控停止，不能无限保持运动目标；
- 调度迟到时只采用 Newmark 补算后的最新状态，不补发过期转矩命令。

### 5.3 外力不得重复进入力矩控制器

Newmark 已把真实 F/T 转换为平台期望运动。迁移后的 `TaskSpaceTorqueController` 只处理：

- 期望状态跟踪；
- 实际机构的质量、惯量、科氏/离心项；
- 真实平台重力及维持绳索预紧所需的广义力；
- 位姿误差反馈。

它的外部交互力输入固定为零。真实 F/T 原始值仍记录，但不第二次加入广义控制力。

## 6. 实际位姿与速度来源

### 6.1 参考程序实际位姿源与迁移选择

参考程序支持两种任务空间实际位姿源：

1. `ForwardKinematics`：正式预规划八绳力矩流程的配置默认值。八轴编码器位置经绞盘、绳索弹性补偿和解析正运动学得到实际六维位姿；
2. `MotionCapture`：持续位姿实验页面默认选择“动捕（实验）”。此时程序仍运行解析FK以获得绳长、弹性补偿和诊断量，但最终送入任务空间控制器的 `feedback.pose` 是Nokov位姿，速度也使用动捕速度。

两种来源都真实存在，不能笼统表述为参考程序只使用FK或只使用动捕。

当前Nokov系统主动发送周期为10 ms，当前六维力Newmark/执行周期为5 ms。10 ms动捕不能保证每个5 ms内环时隙都有新样本，但可以为25 ms任务空间外环提供约2～3个新样本。若迁移采用动捕外环，应采用参考程序同类规则：

- 每个外环时隙只使用当时最新的合格动捕样本；
- 校验接收龄、采样龄、时序不确定度、刚体身份、标定代次和序号；
- 同一动捕样本可以在有效寿命内被内环保持，但不能伪装成5 ms新样本；
- 超过新鲜度上限时退出力矩闭环，不能在运行中静默切换为FK；
- G302 的M2及后续在线张力外环不再并行执行编码器FK。雅可比和张力分配直接使用Nokov实际位姿；编码器Trace仍用于轴级跟随、安全快照和离线FK验算。

若迁移采用FK外环，则八轴同帧编码器位置经当前绞盘模型和解析正运动学产生实际位姿，上一有效位姿作为求解初值，结果必须通过残差、迭代状态、雅可比秩和条件数门限；Nokov继续作为独立低频安全对比。

G302首轮实机方案固定选择Nokov作为任务空间实际位姿源，并在准备阶段检查新鲜度。运行中Nokov失效或超时必须使在线张力结果失效；禁止自动切换为编码器FK，避免反馈源跳变造成转矩突变。

### 6.2 编码器速度

当前六维力的 Newmark 与执行控制周期是 5 ms，目标 Trace 采样周期是 1 ms，二者不是同一个周期。参考程序的八绳力矩 profile 不读取板卡实际速度，也不是把相邻两个 5 ms 控制快照简单相减；它在每次 FIFO 批量读取时逐帧扫描其中全部 1 ms Trace 帧，把每一帧的原始编码器计数送入速度估计器，再由 5 ms 内环或 25 ms 外环消费最新估计结果。

当前程序的 Runtime Trace 读取也会逐帧解析 FIFO，并能取得每帧原始反馈位置、逻辑序号和实际 Trace 周期，因此迁移时应把估计器接在 `HardwareInterface` 的逐帧解码路径，而不是接在 `ControlWorker` 每 5 ms 发布一次的最新快照上。

估计时间基准采用：

```text
t_trace = logical_frame_sequence × actual_trace_period_us
v_k = (q_k - q_{k-1}) / (t_k - t_{k-1})
```

这里的 `actual_trace_period_us` 必须来自本次 profile 配置后的实际周期读回。不得固定除以 1 ms，也不得固定除以 5 ms。

参考程序同时保留三种估计量：相邻帧差分、约100 ms窗口的最小二乘斜率、约10 ms短窗变化守卫。迁移时可复用这一方法，但必须放在力矩 profile 专用的Trace派生反馈层中：

- 只接受连续、可靠、同一 profile generation 的 Trace 帧；
- 逐帧使用逻辑序号和实际 Trace 周期构造板卡序列时间，避免主机批量读取抖动污染差分；
- 相邻序号不连续、丢帧、profile 切换、实际周期变化或时间间隔超限后立即清空速度窗口并重新预热；
- FIFO一次返回多帧时必须按先后顺序全部送入估计器，不能只用最后一帧；
- 5 ms 控制周期没有新 Trace 帧时不得重复使用同一位置伪造零速度；只能在限定新鲜度内保持上一估计，超时则停止；
- 估算速度用于 FK 速度、阻尼和力矩模式超速检查；
- 不改写其他功能模块对“板卡实际速度”的定义。

因此，1 ms Trace 的意义是提高速度估计的数据密度和时间分辨率；5 ms 仍然是当前六维力控制与Newmark的基本周期。速度估计器每1 ms样本更新，并不意味着控制命令改为每1 ms下发。

## 7. Trace 迁移设计

### 7.1 当前与目标对象数

当前阶段 D `ForceInteractionPhysicalRuntime` 共 41 个对象：

- 8 路实际位置；
- 8 路板卡实际速度；
- 8 路状态字；
- 8 路张力；
- 9 个六维 F/T 对象。

建议新增独立 profile：`ForceInteractionPhysicalTorqueRuntime`，仍保持 41 个对象：

- 8 路实际位置；
- 8 路状态字；
- 8 路实际电机转矩；
- 8 路张力；
- 9 个六维 F/T 对象。

也就是用8个实际转矩对象替换8个板卡实际速度对象，速度由编码器位置计算。这样不会因为接入力矩闭环而把对象数从41直接增加到49。

这里“速度由编码器位置计算”特指对FIFO中的每个1 ms Trace帧逐帧更新速度估计器，而不是只对5 ms控制快照差分。`RuntimeTraceSnapshot` 只发布与最新完整Trace帧关联的估计结果、估计窗口起止序号/时间、样本数和有效性；原始1 ms窗口无需复制到每个控制对象中。

### 7.2 Profile 隔离

必须新增独立枚举值和明确的对象契约，不允许根据“当前是否力矩模式”临时改变已有 `ForceInteractionPhysicalRuntime` 的解析含义。原因是：

- 现有速度 D1 已经过实机验证；
- 离线记录和 SafetyMonitor 需要知道每个字段的真实来源；
- profile 切换必须清 FIFO、清主机缓存并增加 generation；
- 速度后端失败后能够恢复原 profile，而不是残留半套对象。

### 7.3 周期

首版保持当前六维力专属 Trace 目标周期 1000 μs：

```text
500 μs总线：trace_cycle = 2
1000 μs总线：trace_cycle = 1
```

准备阶段必须核对配置读回、实际周期、对象数量、对象顺序和同帧完整性。只有实测表明 1 ms 在41对象下不能长期稳定，才另行评估2 ms；不得因为迁移而直接修改全局总线周期。

### 7.4 映射来源

所有轴、张力和从站映射使用当前 G302 配置：

- 电机从站 1001～1008；
- 张力变送器 1009；
- 六维 F/T 1010；
- 当前程序已经验证的逻辑绳索—控制卡轴—张力通道映射。

参考程序中的 G3/Lite 从站表只用于理解机制，不复制数值。

## 8. 多速率控制与线程边界

### 8.1 建议首版时序

```text
Trace采样：          1 ms
F/T与Newmark：       5 ms
0525张力内环：       5 ms
任务空间/分配外环：   25 ms
Nokov反馈：           按硬件新帧发布（抓拍周期约10 ms）
SafetyMonitor：      保持当前独立周期
```

25 ms 外环与 5 ms 内环满足参考程序 `outer = 5 × inner` 的时序约束。每次外环消费当时最新且合格的Nokov帧，并发布带版本号、来源时刻和失效时刻的八路目标张力；内环在其有效期内使用最新目标，过期则停止下发。

这里包含三层不同控制含义：

1. 当前六维力模块的5 ms Newmark属于导纳型运动生成：真实F/T决定期望位姿、速度和加速度；
2. 任务空间外环不是第二个导纳环，而是位姿/速度误差驱动的阻抗型跟踪与逆动力学控制，它把期望运动变成六维广义控制力，再分配为八路目标张力；
3. 0525内环是八根绳索各自独立的标量张力反馈环，同一内环时隙一起更新八轴转矩修正，不是八个互不协调的运动线程。

参考程序在未启用0525时支持1/2/5/10/20/25 ms任务空间周期，默认25 ms；启用0525后要求任务空间外环为张力内环的5～10倍。参考UI的张力内环默认10 ms，因此默认组合会从50 ms外环起；本文建议的5/25 ms是为了与当前六维力5 ms基本周期对齐的迁移起点，不是参考程序唯一配置，也必须经过在线影子计算和实机保持实验确认。

编码器速度估计虽然按每个1 ms Trace帧更新，但不形成第三条命令线程：Trace解码仅更新派生反馈，5 ms内环和25 ms外环分别在自己的绝对主机时钟槽位读取最新且有效的估计值。三个周期的职责必须在日志中分别记录。

如果关闭 0525 张力内环，仍不得默认把任务空间动力学和张力分配塞进每个 5 ms 周期；应先用实测最大耗时证明满足预算，再决定是否采用5 ms单环。正运动学不属于M2及后续在线张力链路的周期预算。

### 8.2 线程职责

- `ControlWorker`：取得一次完整快照、推进 Newmark、调度后端、唯一地下发命令；
- 外环计算线程：FK、任务空间动力学和张力分配，只使用输入副本，不触碰硬件；
- HardwareThread：执行 Trace API 和八轴批量转矩命令；
- SafetyMonitor线程：读取发布快照并独立裁决；
- 记录线程：异步写盘，绝不阻塞控制线程。

外环使用单槽请求/单槽结果。新请求不得排成长队；过时结果按 epoch、来源序号和截止时间丢弃。

## 9. 张力分配、0525内环与参数职责

### 9.1 三种不同“上下限”不得混淆

1. **分配器张力边界**：决定目标广义力是否存在可行的八绳张力解，是控制算法约束；
2. **D1 SafetyMonitor 张力上下限**：判断实测张力是否危险，是全局安全保护；
3. **电机实际转矩上限**：限制驱动实际转矩，是另一条全局安全保护。

分配器边界应位于全局安全边界内部并留有裕量，但分配器“无可行解”和实测张力“越过安全线”是两种不同故障，日志中必须分开。

### 9.2 0525参数

参考程序明确把0525张力内环首版限制在Lite模板；Lite实物与当前G302使用同型号电机和张力变送器，因此其0525参数、转矩换算和内环时序具有较强的直接复用基础。迁移首版可把这些值作为G302在线张力模式的默认参数种子，但在线运行只读取冻结副本：

- 不要求用户勾选【位姿控制模块】中的“力控线程”或“完全力控”；
- 进入六维力在线张力模式前，旧力控线程必须关闭；
- 只复用参数和算法，不复用旧线程所有权；
- 参数来源、哈希和冻结时间写入运行元数据。

可以优先继承并逐项核对的参数包括：0525每通道Kp/Ki/Kd、死区、转矩修正上限、转矩变化率、内环周期、额定转矩到反馈值的换算，以及同型号张力变送器的比例和符号。当前G302已经验证过的轴—张力通道映射优先级更高，不能被Lite旧映射覆盖。

任务空间Md/K/阻尼比只能作为首轮试验起点，不能因为电机和变送器相同就直接视为已验收。它们还受平台质量与惯量、绞盘有效半径、绳索几何、预紧水平、位姿反馈源及其周期影响。方向/负载前馈、摩擦和弹性补偿参数同样需要核对当前机械状态。

后续可以在六维力模块中提供独立参数配置，但仍由同一配置结构校验，不复制一套新的PID实现。

### 9.3 目标张力变化率

目标张力及对应基础转矩必须使用分配器连续性权重、转矩斜率限制和内环输出斜率限制。禁止把突变的 Newmark 参考直接转成突变电机转矩。任何限幅都要记录“未限幅请求、最终命令和限幅原因”，不能静默改变动力学效果。

## 10. 硬件适配层

### 10.1 当前缺口

当前 `HardwareInterface` 已有单轴 `motorTorqueStart()` 和 `motorTorqueChange()`，也已经具备实际转矩 Trace 解析能力，但缺少参考程序使用的完整八轴快速批量接口、批量结果诊断以及力矩模式安全退出接口。

### 10.2 只迁移最小硬件能力

建议在当前 `HardwareInterface` 增加：

- `TorqueBatchResult`；
- `motorTorqueStartBatchFast()`；
- `motorTorqueChangeBatchFast()`；
- `motorTorqueReturnToPositionHold()`；
- 批量命令的首/末轴时间、API耗时、失败轴和部分下发标志。

这些接口只封装现有单轴雷赛调用和硬件线程队列，不包含 Newmark、张力PID或UI判断。

八轴批量命令只要出现部分成功，就必须立即触发既有全轴安全停止，并把“已成功轴数、失败轴、SDK返回值”写入日志。

### 10.3 命令所有权

新增统一执行模式枚举，例如：

```cpp
enum class ForceInteractionExecutionMode {
    OnlineVelocity,
    OnlineTensionTorque
};
```

该值在准备阶段冻结。`ControlWorker` 同一时刻只允许一个后端持有八轴命令权，并继续排斥：

- 旧力控线程/完全力控；
- PVT；
- 末端遥控；
- Trace延迟标定；
- 单轴点位、JOG和调试命令；
- 其他转矩模式测试。

## 11. 会话状态机与停车

### 11.1 建议状态

```text
Idle
 → Prepared
 → WaitingForReliableTrace
 → PretensionQualifying
 → TorqueHandover
 → Holding
 → InteractiveRunning
 → Braking
 → ControlledUnload
 → PositionHold
 → Completed
```

任一阶段都可以进入 `Fault`。状态机属于新力矩后端，不修改阶段 B/C 和现有速度后端的状态定义。

### 11.2 启动资格

启动转矩命令前至少确认：

- 当前为阶段 D1，绞盘、绳索和平台已接入；
- 八轴使能且状态字为 Operation enabled；
- F/T、八轴位置、八轴实际转矩、八路张力和状态字来自可靠新鲜帧；
- 张力通道映射已冻结并通过实物确认；
- 实测张力处于 SafetyMonitor 范围和分配器允许范围；
- 电机速度、实际转矩变化率、位姿误差、FK残差和条件数满足门限；
- 初始目标转矩与实测转矩差满足交接限制；
- 当前实际位姿与 Newmark 初始位姿一致；
- 全局实际转矩保护、D1张力保护和控制快照看门狗均已启用；
- Nokov如选择“仅监测”，必须已有新鲜起点快照，但不要求每个控制周期到达。

### 11.3 正常停止

用户停止、最长时间到达、力释放或动态边界触发时：

1. 当前六维力前端冻结外力输入；
2. 当前 Newmark/制动逻辑生成连续减速参考；
3. 力矩后端继续跟踪该参考并保持张力；
4. 平台速度和位姿稳定后进入短时力矩保持；
5. 按冻结策略受控卸载控制修正；
6. 调用全轴停止并返回当前位置保持；
7. 结束记录并恢复普通 Trace profile。

不得在正常停止时直接把八路转矩清零，也不得在尚未稳定时在线切回速度模式。

### 11.4 故障停止

下列情况直接走现有安全急停，不尝试继续闭环卸载：

- 控制快照超时或硬件断连；
- Trace丢失、对象不完整或profile变化；
- 驱动状态异常；
- 实测张力越过全局安全上下限；
- 实际电机转矩越过全局上限；
- 八轴转矩批量下发部分失败；
- FK或张力分配出现非数值、秩不足或持续无可行解；
- 工作空间硬边界或绞盘硬行程触发。

驱动抱闸能防止失能后平台下落，但不替代运行中的上述故障处理。

## 12. SafetyMonitor 接入边界

集中式 SafetyMonitor 继续负责：

- 控制快照停更；
- 控制卡连接和驱动状态；
- 八路实测张力上下限及断绳；
- 实际电机转矩上限；
- 电机行程和超速；
- 工作空间硬边界；
- 软件看门狗和急停锁存。

新后端内部只负责控制有效性：反馈新鲜度、参考过期、FK质量、位姿跟踪、张力分配可行性、目标/命令斜率和两阶段提交。不要在后端再造一份与 SafetyMonitor 数值独立的“实测张力安全保护”。

对于专用力矩 Trace profile，SafetyMonitor 的状态字、张力和实际转矩必须明确识别该 profile；编码器差分速度应通过专用字段提供，不能冒充板卡速度而不记录来源。

## 13. UI方案

### 13.1 页面边界

不复制参考程序完整的【8绳力矩参数】页。建议在【六维力交互】-【实机力交互（阶段D）】中增加：

- 执行方式：`在线速度控制（现有，默认）` / `在线张力-力矩控制（实验）`；
- 一个“在线张力控制参数”折叠区或独立子页；
- 当前后端、Trace profile、内/外环周期、张力内环开关和准入摘要。

阶段D主页面只保留必要操作和结果，详细 Md/K/D、分配器与0525参数放在参数区，避免再次把监测文本和运行逻辑绑在一起。

### 13.2 参数冻结

点击“准备阶段D”时冻结：

- 执行方式；
- 六维任务空间 Md/K/阻尼比；
- 分配器张力边界、偏置、连续性与转矩边界；
- 0525开关及参数快照；
- 内外环周期；
- 绞盘、几何、轴/传感器映射；
- F/T零点、安装变换、Newmark参数；
- 全局安全阈值和Trace配置。

准备后修改任一关键参数必须使准备态失效，不允许运行中热切换。

## 14. 记录与离线验算

继续使用当前六维力交互运行文件，在元数据中增加：

- `execution_mode`；
- 控制器、分配器、0525和时序配置版本/哈希；
- Trace对象契约和实际周期；
- FK来源及质量门限；
- 转矩量化比例和硬件上限。

每个控制/内环周期至少记录：

- F/T原始值、去零值、滤波值和进入Newmark值；
- Newmark期望位姿、速度、加速度；
- FK实际位姿、速度、残差、迭代状态和条件数；
- 六维位姿/速度误差；
- 惯性、前馈和反馈广义力；
- 八路目标张力、实测张力和误差；
- 八路基础转矩、PID修正、限幅前请求、最终命令和实测转矩；
- 内外环版本、来源时间、截止时间、迟到/跳周期；
- 命令是否尝试、是否成功、部分下发轴和API耗时；
- SafetyMonitor状态与最终停车原因。

“验算最近运行”应根据 `execution_mode` 选择验算器：速度模式保持现有逻辑；张力模式重新计算任务空间控制、张力分配、转矩限幅和命令提交，不能继续只比较编码器反算轨迹。

## 16. 分阶段实施计划（开发与验收流程，不是UI运行阶段）

M0～M5用于约束开发、代码审查和实机验收顺序，不应作为六个按钮或六个运行模式放到UI。正式UI只需要保留用户实际要选择的执行方式、准备/启动/停止、必要参数和诊断结果。

在线影子计算可在开发版本中通过受控诊断开关启用，验证完成后可以隐藏为维护功能；M0纯算法、M1离线复算等阶段不属于操作者日常界面。

### M0：纯算法迁移

- 迁入任务空间控制器、冗余分配器和0525张力反馈；
- 消除旧 G3/Lite、旧 UI、旧硬件和预规划轨迹依赖；
- 增加数值自检：零误差、重力平衡、可行/不可行张力、转矩方向、斜率限制、非数值输入；
- 与参考程序固定输入输出做回归比对。

验收：不连接硬件即可运行，算法文件不包含 `HardwareInterface` 或 `MainWindow`。

### M1：离线影子计算

- 读取现有D1日志和配置；
- 用同一Newmark期望状态离线计算目标张力和转矩；
- 不下发硬件；
- 核对方向、数量级、可行性、最大耗时和参数敏感性。

验收：结果可复现，全部输入和参数可追溯，无隐式读取全局状态。

### M2：在线影子模式

- 保持现有在线速度后端实际控制；
- 新力矩后端只读取同一参考与反馈并记录候选结果；
- 不允许两个后端同时下发；
- 验证1 ms、41对象Trace和25 ms外环预算。

验收：现有D1运动不受影响；影子计算无过期、无任务堆积，SafetyMonitor正常。

### M3：静态预紧与保持

- 新增批量转矩接口和专用Trace profile；
- 只在已接绳、已预紧、平台静止的D1中进入力矩模式；
- 验证交接、短时保持、用户停止、受控卸载和回位置保持；
- 暂不输入交互力。

验收：无明显转矩跳变，张力保持在分配范围和全局安全范围内，停止路径可重复。

### M4：单轴小力平移

- 只开三维平动，逐轴施加小力；
- 比较Newmark期望、Nokov在线实际、目标/实测张力和命令/实测转矩；编码器FK只在运行后离线复核；
- 与同条件在线速度D1做对照。

验收：方向正确、动态连续、误差和张力变化可解释，所有停车机制有效。

### M5：姿态与完整六维

- 在专用姿态可行域、绳索干涉和张力可行性表完成后，依次开放Mx/My/Mz；
- 最后才开放多轴六维组合输入。

验收：符合《六维力交互姿态调试说明》的边界和调试顺序。

## 17. 明确不做的事情

- 不删除或替换当前已经跑通的在线速度D1；
- 不让用户手动同时开启旧“力控线程/完全力控”和六维力张力后端；
- 不把参考程序整份 `MainWindow`、`ControlWorker` 或 `HardwareInterface` 合并进来；
- 不沿用参考程序的从站号、轴序或张力通道数值；
- 不用Nokov低频帧直接驱动5 ms转矩内环；
- 不在实时线程写CSV或执行阻塞式文件操作；
- 不在Newmark和任务空间控制器中重复施加F/T外力；
- 不把目标张力分配边界当成全局实测张力安全保护；
- 不在未接绳空转状态下启动闭环电机转矩控制。

## 18. 最终建议

迁移应以“新增执行后端”而不是“更换六维力主控制器”为核心。当前F/T、Newmark、边界、SafetyMonitor和记录体系继续作为唯一上层；参考程序只提供任务空间控制、张力分配、0525内环及力矩模式生命周期的经过筛选的实现经验。

首个可交付目标不是立即做真实交互，而是完成 M0～M2：同一D1运行中，速度后端照常控制，新力矩后端在线影子计算并留下可离线复算的完整记录。只有影子结果、Trace容量和计算预算都通过后，才进入实际转矩交接。这条路径对当前已验证功能影响最小，也最容易定位迁移问题。

- Nokov原始抓拍约10 ms一帧，采集线程按SDK新帧发布不可变快照；UI显示频率不再限制控制数据更新率；

### 19.5 已知的5 ms调度现象与当前处置

同次Release运行中，六维力计算中位数/最大值为38/162 us，完整命令循环中位数/95分位为1.879/2.784 ms，但2861次命令仍统计到286个5 ms漏周期；命令间隔中位数为5.051 ms，95分位为10.727 ms，说明剩余漏周期主要来自Windows/Qt事件循环、ControlWorker与HardwareThread协作及控制卡API的调度抖动，而不是M2或动力学计算超时。

这里的“漏周期”是上位机错过一次5 ms命令更新时间，不是EtherCAT总线丢帧、Trace丢帧或CSV丢记录。本次Trace无效/非递增为0/0，记录接受/写入/丢弃为2861/2861/0。程序会补算Newmark模型时间，但无法补发已经错过时刻的电机命令。

当前决定是保留该现象作为已知限制，不阻塞M3静态预紧开发；但M3必须继续记录命令间隔、漏周期、控制卡API耗时和张力响应。M3仅允许无交互力的短时静态预紧与保持，不得据此直接开放M4平动交互或M5姿态力矩。若实际张力出现明显超调、振荡或连续10 ms以上不更新，应停止M3并优先整改5 ms执行调度。
