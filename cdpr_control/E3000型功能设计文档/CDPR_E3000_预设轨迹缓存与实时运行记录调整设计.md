# CDPR E3000 预设轨迹缓存与实时运行记录调整设计

## 1. 调整目的

当前八轴速度闭环在点击“开始”后，先在硬件控制线程同步导出完整 `expected_trajectory.csv`。20 s轨迹采用1 ms周期时共有20001点，导出约需4.8 s；5 ms周期共有4001点，约需0.95 s。该等待与电机、Trace和PID无关，只是启动路径包含了大文件写盘。

本次调整目标是：预设轨迹在“生成轨迹”阶段完成校验和落盘；“开始8轴闭环”只完成硬件检查、Trace复位、时间锚点和运动启动。八轴PID、速度前馈、保护算法和主机时间基准保持不变。

## 2. 数据生命周期

### 2.1 轨迹生成阶段

`CdprCoordinator`完成五次多项式、逆运动学和八轴轨迹校验后，将期望轨迹写入程序目录下的轨迹缓存：

```text
trajectory_cache/<planId>/expected_trajectory.csv
```

`expectedTrajectorySha256`使用轨迹CSV的SHA-256；`planId`再将该哈希与结构配置快照共同计算，避免结构配置不同但离散轴轨迹偶然相同的记录共用身份。轨迹对象同时保存：

- `planId`；
- 缓存文件绝对路径；
- 文件SHA-256；
- 生成时使用的结构配置快照。

只有缓存写入和哈希校验成功，轨迹才标记为有效并允许启动。轨迹参数、控制周期或结构配置变化后，现有失效逻辑继续清空轨迹对象，因此不会误用旧文件。同一轨迹可以重复运行并复用缓存。

### 2.2 启动阶段

八轴速度闭环启动顺序调整为：

```text
校验plan与缓存文件
→ 设置八轴脉冲当量
→ 创建轻量运行目录及记录文件
→ 在run_context.json写入planId、缓存路径和SHA-256
→ 配置并复位Trace
→ 获取八轴同一新鲜Trace帧并建立锚点
→ 开始周期控制
```

启动阶段不再遍历或复制完整轨迹，也不再因导出期间积压Trace而重复配置Trace。正常剩余等待只包括Trace首帧和五次多项式速度越过启动阈值，预计为几十毫秒。

### 2.3 运行结束与分析

一致性分析器读取期望轨迹时采用兼容顺序：

1. 若运行目录内存在 `expected_trajectory.csv`，按旧格式读取；
2. 否则读取 `run_context.json` 中的缓存路径；
3. 校验缓存文件SHA-256与记录值一致；
4. 校验失败则停止分析，禁止静默使用其他轨迹。

离线PVT暂时保留旧方式，即每次运行目录仍包含独立的期望轨迹文件，避免本次调整影响已验证的PVT启动与锚点逻辑。

## 3. 并发与异常处理

- 轨迹导出在CDPR协调线程执行，不占用硬件控制线程；导出完成前启动按钮不可用。
- 每次速度闭环生成请求带有递增代次；参数变化会立即推进代次，后台旧任务即使稍后完成也会被UI丢弃，不会重新启用旧轨迹。
- 缓存文件采用 `QSaveFile` 原子提交，避免中断后留下半文件。
- 启动前重新计算SHA-256；文件缺失或被修改时拒绝运动并要求重新生成。
- 运行记录保存绝对路径、`planId`和SHA-256，使故障复盘能够确认期望轨迹来源。

## 4. 与实时力交互的关系

实时力交互没有完整的预设轨迹，不能复用“启动前导出CSV”的假设。其周期链路为：

```text
F/T当前样本 → Newmark单步 → 逆运动学
→ 八轴期望位置/速度 → PID与速度命令
```

未来为其增加结构化周期记录帧，内容至少包括F/T输入、末端期望状态、八绳期望状态、八轴反馈、PID输出和保护状态。控制线程只向内存环形队列写入一帧，记录线程异步落盘。

因此两类数据源共享同一运行记录框架，但期望数据来源不同：

- 预设轨迹：运行记录引用已缓存的静态轨迹；
- 实时力交互：期望状态随控制周期产生并异步记录。

## 5. 验收条件

1. 1 ms和5 ms轨迹在生成完成后均可立即进入启动流程，不再出现与轨迹点数成正比的秒级等待。
2. 八轴控制周期、PID命令、Trace锚点和跟随误差结果与调整前一致。
3. 同一预设轨迹可重复运行，每次生成独立反馈记录并自动完成一致性分析。
4. 修改或删除缓存文件后，启动或分析能够明确报错。
5. 旧运行目录仍可由分析器读取，不破坏已有测试数据。
